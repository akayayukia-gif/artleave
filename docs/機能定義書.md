# 機能定義書

## システム名：Artリーブ
文書番号：C101　版：ver2.0

---

## 1. 文書の目的

本書は、「1シート企画書（企画草案）」で定義したコンセプト・解決案をもとに、Artリーブが備える機能を一覧化し、各機能の仕様（利用者・入力・処理・出力・関連データ）を明確にすることを目的とする。
開発時の実装範囲の認識合わせ、および企業へのプレゼン資料作成時の技術的な説明の裏付け資料として使用する。

---

## 2. システム概要

| 項目 | 内容 |
|---|---|
| システム名 | Artリーブ |
| 概要 | オリジナルキャラクター（オリキャラ）のビジュアルと設定、世界観、相関関係を一元管理する個人クリエイター向けWebサービス |
| 主な利用者 | イラスト・漫画・小説などを創作する個人クリエイター |
| 提供形態 | Webアプリケーション（ブラウザ利用） |
| 関連文書 | 1シート企画書（企画草案）C101 |

## 4. 機能詳細定義

### F-01　ユーザー認証機能

| 項目 | 内容 |
|---|---|
| 概要 | クリエイターがサービスを利用するためのアカウント登録・ログイン・ログアウトを行う |
| 利用者 | クリエイター（本人） |
| 入力 | メールアドレス、パスワード（新規登録時）／ログイン情報（メールアドレス、パスワード） |
| 処理内容 | 1. 新規登録時にアカウント情報を作成する<br>2. ログイン時に入力情報を照合し、認証する<br>3. ログアウト処理を行う<br>4. パスワードを忘れた場合に再設定する |
| 出力／画面要素 | 新規登録画面、ログイン画面、パスワード再設定画面 |
| 関連データ | ユーザーテーブル（ID、メールアドレス、パスワード（ハッシュ化）、登録日） |
| 備考 | 他の全機能の前提となる基盤機能。各データはユーザーIDに紐づけ、他ユーザーからアクセスできないようにする |

### F-02　キャラクター管理機能

| 項目 | 内容 |
|---|---|
| 概要 | キャラクターごとに専用ページを作成し、基本プロフィールとイラストを紐づけて管理する |
| 利用者 | クリエイター（本人） |
| 事前条件 | ログイン済みであること（F-01） |
| 入力 | キャラクター名、性格、年齢、種族、所属陣営、プロフィール文、タグ、紐づけるイラスト |
| 処理内容 | 1. 新規キャラクターページを作成する<br>2. 入力項目を保存する<br>3. 既存キャラクターの情報を編集・削除する |
| 出力／画面要素 | キャラクター一覧画面、キャラクター詳細ページ（プロフィール表示エリア、イラスト表示エリア） |
| 関連データ | キャラクターテーブル（ID、名前、性格、年齢、種族、陣営、プロフィール文、作成日、更新日） |
| 備考 | F-03（タグ）、F-04（検索）、F-09（画像管理）と連携する |

### F-03　タグ管理機能

| 項目 | 内容 |
|---|---|
| 概要 | キャラクターや設定に付与するタグを作成・編集・削除し、検索の軸として管理する |
| 利用者 | クリエイター（本人） |
| 入力 | タグ名、タグの分類（種族／陣営／属性等、任意） |
| 処理内容 | 1. 新しいタグを作成する<br>2. 既存タグの名称を編集する<br>3. 不要なタグを削除する（削除時は紐づくキャラクターからも解除される）<br>4. タグの一覧を表示する |
| 出力／画面要素 | タグ管理画面（タグ一覧、作成・編集フォーム） |
| 関連データ | タグテーブル（ID、タグ名、分類）、キャラクタータグ関連テーブル |
| 備考 | F-02（キャラクター管理）のタグ入力、F-04（検索）の検索条件として利用される |

### F-04　検索・絞り込み機能

| 項目 | 内容 |
|---|---|
| 概要 | タグや属性を条件にキャラクターを絞り込んで表示する |
| 利用者 | クリエイター（本人） |
| 入力 | タグ、種族、所属陣営などの検索条件 |
| 処理内容 | 1. 入力された条件に合致するキャラクターをデータベースから抽出する<br>2. 一覧表示を更新する |
| 出力／画面要素 | 絞り込み後のキャラクター一覧 |
| 関連データ | キャラクターテーブル、タグテーブル（F-03） |
| 備考 | 複数条件のAND検索に対応する |

### F-05　世界観・用語集管理機能

| 項目 | 内容 |
|---|---|
| 概要 | 世界の設定、歴史、特殊能力のルール、専門用語などを階層構造で登録・閲覧する |
| 利用者 | クリエイター（本人） |
| 入力 | 用語名、説明文、親となる用語（階層構造を作る場合）、関連するキャラクター |
| 処理内容 | 1. 用語ページを新規作成・編集する<br>2. 親子関係を設定して階層構造を構築する<br>3. キャラクターページとの相互リンクを設定する |
| 出力／画面要素 | 用語集ツリー表示画面、用語詳細ページ（関連キャラクター一覧を含む） |
| 関連データ | 用語テーブル（ID、用語名、説明文、親ID）、キャラクター用語関連テーブル |
| 備考 | F-02のキャラクター詳細ページから用語ページへ遷移できる |

### F-06　エピソード・ストーリー管理機能

| 項目 | 内容 |
|---|---|
| 概要 | キャラクターや世界観に関わるエピソード・出来事を時系列で記録し、あとから振り返れるようにする |
| 利用者 | クリエイター（本人） |
| 入力 | エピソードタイトル、本文、発生時期（作中の時系列、任意）、関連するキャラクター・用語 |
| 処理内容 | 1. エピソードを新規作成・編集する<br>2. 関連キャラクター・用語とリンクさせる<br>3. 時系列順またはキャラクター別に一覧表示する |
| 出力／画面要素 | エピソード一覧画面（時系列表示）、エピソード詳細ページ |
| 関連データ | エピソードテーブル（ID、タイトル、本文、発生時期、作成日）、エピソード関連テーブル（エピソードID、キャラクターID／用語ID） |
| 備考 | F-02（キャラクター管理）、F-05（用語集）の各詳細ページから関連エピソードを辿れるようにする |

### F-07　相関図機能

| 項目 | 内容 |
|---|---|
| 概要 | キャラクター同士の関係性（敵対・血縁・友人等）を図として登録・閲覧する |
| 利用者 | クリエイター（本人） |
| 入力 | 関係の起点キャラクター、終点キャラクター、関係の種類（ラベル） |
| 処理内容 | 1. 2つのキャラクターを線で結び、関係ラベルを設定する<br>2. 相関図を自動レイアウトして描画する<br>3. ノードをクリックするとキャラクター詳細ページへ遷移する |
| 出力／画面要素 | 相関図エディタ画面（ノード＝キャラクター、エッジ＝関係性） |
| 関連データ | 相関関係テーブル（起点キャラクターID、終点キャラクターID、関係ラベル） |
| 備考 | キャラクター数が多い場合のレイアウト崩れを考慮し、手動でのノード位置調整機能を持たせる |

### F-08　リファレンスサイドバー機能

| 項目 | 内容 |
|---|---|
| 概要 | イラスト制作や執筆の作業中に、画面端から呼び出してキャラクター資料を常時表示する |
| 利用者 | クリエイター（本人） |
| 入力 | 表示したいキャラクターの選択 |
| 処理内容 | 1. サイドバーを画面端からスライド表示する<br>2. 選択したキャラクターの衣装設定・カラーパレット・マネキンを表示する<br>3. 表示中も裏の画面の操作を妨げないようにする |
| 出力／画面要素 | フローティングサイドバー（衣装設定表示エリア、カラーパレット表示エリア、マネキン表示エリア） |
| 関連データ | キャラクターテーブル、イラストテーブル、カラーパレットテーブル（F-10）、マネキンテーブル（F-11） |
| 備考 | ワンクリックでの開閉、表示キャラクターの切り替えに対応する |

### F-09　画像管理機能

| 項目 | 内容 |
|---|---|
| 概要 | キャラクターのイラスト（表情差分・衣装違い等）をアップロード・表示・差し替えする |
| 利用者 | クリエイター（本人） |
| 入力 | 画像ファイル、画像に紐づけるキャラクター、画像の種類（表情差分／衣装違い等のラベル） |
| 処理内容 | 1. 画像をアップロードする<br>2. 表示用にリサイズ・最適化する<br>3. キャラクターページに紐づけて保存する<br>4. 既存画像を差し替え・削除する |
| 出力／画面要素 | 画像アップロード画面（ドラッグ＆ドロップ対応）、キャラクター詳細ページの画像ギャラリー |
| 関連データ | イラストテーブル（ID、キャラクターID、画像ファイルパス、種類ラベル、アップロード日） |
| 備考 | 対応形式（例：jpg, png）とファイルサイズ上限を定める |

### F-10　カラーパレット管理機能

| 項目 | 内容 |
|---|---|
| 概要 | キャラクターごとに使用する色（肌・髪・瞳・衣装等）のカラーパレットを作成・保存し、資料として参照できるようにする |
| 利用者 | クリエイター（本人） |
| 入力 | 色名（任意）、カラーコード、用途ラベル（肌／髪／瞳／衣装等）、紐づけるキャラクター |
| 処理内容 | 1. カラーコードを登録し、パレットに追加する<br>2. 既存パレットの編集・削除を行う<br>3. キャラクターページ・サイドバーにパレットを表示する |
| 出力／画面要素 | カラーパレット編集画面（カラーピッカー、登録済み色の一覧）、キャラクター詳細ページ・サイドバー内のパレット表示エリア |
| 関連データ | カラーパレットテーブル（ID、キャラクターID、色名、カラーコード、用途ラベル） |
| 備考 | F-08（リファレンスサイドバー）に表示する主要な資料のひとつ |

### F-11　マネキン作成機能

| 項目 | 内容 |
|---|---|
| 概要 | キャラクターごとに、体格やプロポーションの基準となる「マネキン（ボディベース）」を作成・保存する。イラスト制作時の体型のブレを防ぐ資料として使う |
| 利用者 | クリエイター（本人） |
| 入力 | 身長、頭身、体格タイプ（骨格の太さ等）、肌の色、基準となるポーズの選択、紐づけるキャラクター |
| 処理内容 | 1. 各パラメータを入力・選択する<br>2. パラメータに応じたベースシルエットを生成する<br>3. キャラクターページに紐づけて保存する<br>4. 既存マネキンの編集、または別キャラクターへの複製を行う |
| 出力／画面要素 | マネキン作成・編集画面（パラメータ入力フォーム、シルエットのプレビュー表示）、キャラクター詳細ページ内のマネキン表示エリア |
| 関連データ | マネキンテーブル（ID、キャラクターID、身長、頭身、体格タイプ、肌の色、ポーズID、更新日） |
| 備考 | F-08（リファレンスサイドバー）から呼び出せるようにし、作業中すぐに体型を確認できるようにする。初期実装は簡易シルエット・頭身ガイド表示とし、将来的にポーズ変更や3D表示への拡張を検討する |

### F-12　テーマ切替機能

| 項目 | 内容 |
|---|---|
| 概要 | 登録している世界観の雰囲気に合わせて、画面全体のカラーテーマを切り替える |
| 利用者 | クリエイター（本人） |
| 入力 | テーマの選択（例：ダークモード、ファンタジー風、サイバー風） |
| 処理内容 | 1. 選択したテーマに応じて配色・UIの質感を切り替える<br>2. 選択状態を保存し、次回ログイン時も反映する |
| 出力／画面要素 | テーマ選択画面、アプリ全体のUI配色 |
| 関連データ | ユーザー設定テーブル（ユーザーID、選択中テーマ） |
| 備考 | 初期実装はダークモード／ライトモードの2種を想定し、将来的にテーマの種類を拡張する |

### F-13　変更履歴・バージョン管理機能

| 項目 | 内容 |
|---|---|
| 概要 | キャラクターや用語集などの設定が「いつ・どのように変更されたか」を記録し、過去の状態を遡って確認できるようにする |
| 利用者 | クリエイター（本人） |
| 入力 | （自動記録）編集対象の項目、変更前後の内容、変更日時 |
| 処理内容 | 1. キャラクター・用語集等の編集が行われるたびに変更内容を記録する<br>2. 変更履歴の一覧を表示する<br>3. 過去の内容を閲覧する（差分表示）<br>4. 必要に応じて過去の内容に戻す |
| 出力／画面要素 | 変更履歴一覧画面、差分表示画面 |
| 関連データ | 変更履歴テーブル（ID、対象種別、対象ID、変更前内容、変更後内容、変更日時） |
| 備考 | 設定崩壊の防止という本サービスの中心的な価値に直結する機能。F-16（矛盾検知アシスタント機能）の判定材料としても利用する |

### F-14　データエクスポート機能

| 項目 | 内容 |
|---|---|
| 概要 | キャラクターページや設定資料をPDF・画像として書き出し、資料として保存・印刷・配布できるようにする |
| 利用者 | クリエイター（本人） |
| 入力 | 書き出し対象（キャラクター単体／複数選択）、書き出し形式（PDF／画像） |
| 処理内容 | 1. 書き出し対象と形式を選択する<br>2. 選択内容をもとにファイルを生成する<br>3. ファイルをダウンロードする |
| 出力／画面要素 | エクスポート設定画面、ダウンロードされたPDF／画像ファイル |
| 関連データ | キャラクターテーブル、イラストテーブル（書き出し対象の参照のみ） |
| 備考 | 印刷して紙の資料として使いたいというニーズにも対応する |

### F-15　公開共有機能（将来拡張）

| 項目 | 内容 |
|---|---|
| 概要 | 自分の設定資料集ページを、パスワード付き、または一般向けにWebサイトとして公開する |
| 利用者 | クリエイター（本人）／閲覧者（公開先） |
| 入力 | 公開範囲の設定（限定公開／一般公開）、公開用パスワード（限定公開の場合） |
| 処理内容 | 1. 公開用の固有URLを発行する<br>2. 公開設定に応じて閲覧制限をかける<br>3. 閲覧者には編集不可の閲覧専用画面を表示する |
| 出力／画面要素 | 公開設定画面、公開用閲覧ページ |
| 関連データ | 公開設定テーブル（ユーザーID、公開URL、公開範囲、パスワード） |
| 備考 | 本機能はver2.0以降での実装を想定する |

### F-16　矛盾検知アシスタント機能（将来拡張）

| 項目 | 内容 |
|---|---|
| 概要 | 新しく追加した設定やエピソードが、既存の設定と矛盾していないかを指摘する。費用をかけないため、自作の「ルールチェック」を基本とし、自由記述の文章の矛盾を見たい利用者だけが「AIチェック（Gemini API 無料枠）」を追加で使える |
| 利用者 | クリエイター（本人） |
| 入力 | チェック対象（キャラクター／用語／エピソード）、AIチェックを使うかどうか（設定画面で利用者が選択） |
| 処理内容 | 1. ルールチェック（自作・無料）：登録済みの項目同士を自分のコードで照合する（下表）<br>2. AIチェック（任意）：利用者がオンにしている場合のみ、対象と関連する設定の文章をGemini APIに送り、文章中の矛盾を指摘させる<br>3. 両方の指摘を「ルール」「AI」の区別を付けて一覧表示する（最終判断はクリエイターが行う） |
| 出力／画面要素 | 矛盾チェック結果パネル、設定画面のAIチェック利用設定（データ送信の説明つき） |
| 関連データ | キャラクター、用語、エピソード、相関関係、カラーパレット、マネキン、変更履歴（F-13）、矛盾チェック結果、ユーザー設定 |
| 備考 | ver2.0以降での実装を想定し、ルールチェックを先に作る。誤検知を前提に、あくまで「提案」の位置づけとする。Gemini APIの無料枠では送った内容がGoogleのサービス改善に使われるため、AIチェックは初期状態でオフとし、利用者が説明を読んで自分でオンにした場合のみ使う。画像は送らず、文章のみ送る |

ルールチェックの内容

| ルールID | 内容 | 例 |
|---|---|---|
| R-01 | 相関関係の向きの矛盾 | AからBが「兄」、BからAも「兄」になっている |
| R-02 | プロフィール文とカラーパレットの色の食い違い | 文章では「青い瞳」なのに、パレットの瞳の色が赤系 |
| R-03 | プロフィール文とマネキンの身長の食い違い | 文章では「身長158cm」なのに、マネキンは170cm |
| R-04 | エピソードの時系列の逆転 | 並び順は後なのに、作中時期の年号（「王国暦312年」等）が前のエピソードより小さい |
| R-05 | 名前の重複・表記ゆれ | 同じ名前のキャラ・用語が2つある、「エルフ」と「ｴﾙﾌ」が別の種族として登録されている |
| R-06 | エピソード本文と関連キャラの登録漏れ | 本文に登場するキャラ名が、そのエピソードの関連キャラに登録されていない |

## 5. 非機能要件

| 分類 | 要件 |
|---|---|
| ユーザビリティ | クリエイターが愛着を持って使えるよう、ダーク基調で没入感のあるUIとする |
| パフォーマンス | 画像表示・サイドバー開閉など、操作のレスポンスが体感できるレベルで遅延しないこと |
| データ保全 | 登録した設定・イラストが意図せず失われないよう、保存処理と変更履歴（F-13）を明確にする |
| セキュリティ | ユーザーごとのデータが他ユーザーから参照・編集されないようにする（F-01） |
| 拡張性 | F-15・F-16など将来機能を見据え、テーブル設計に余地を持たせる |

## 6. 使用技術

採用方針：目的なく最新技術を入れるのではなく、各機能の要件に対して明確に効く箇所にのみ採用する。基本構成はシンプルな構成に寄せ、表現力や開発効率が大きく上がる部分（相関図描画、AI機能等）に絞って最新技術を使う。

| 分類 | 採用技術 | 選定理由・主な関連機能 |
|---|---|---|
| フロントエンド | Next.js（React）＋ TypeScript | フロント・API処理を1つのプロジェクトで完結でき、個人開発でもフルスタックに実装しやすい。型安全によりF-02〜F-14の複雑なデータ構造の受け渡しミスを防ぐ |
| スタイリング | Tailwind CSS | F-12テーマ切替機能で求められるダークモード・配色切替を、CSS変数ベースで軽量に実装できる |
| バックエンド | Next.js Server Actions / API Routes（Node.jsサーバーとして常時起動） | サーバーレス前提ではなく、自宅サーバー上で`next start`により常駐プロセスとして稼働させる。F-01認証処理、F-13変更履歴の記録処理に使用 |
| データベース | PostgreSQL ＋ Prisma（ORM） | キャラクター・タグ・用語・相関関係など多対多を含む複雑なリレーションを型安全に扱える（F-02〜F-14全般）。自宅サーバー上にDockerコンテナとして構築し、クラウドDBの月額費用をかけない |
| 認証 | Auth.js（NextAuth） | 自前でパスワード管理の仕組みを一から作らず、安全な認証を短期間で実装できる（F-01） |
| 画像ストレージ | ローカルディスク（USB接続SSD）＋ Sharp（画像最適化） | イラスト画像を自宅サーバーのストレージに保存し、外部サービスの費用をかけない（F-09） |
| 相関図描画 | React Flow | ノード（キャラクター）とエッジ（関係性）から成る相関図を、ドラッグ操作込みで短期間で実装できる（F-07） |
| マネキン表示 | SVG＋Canvas API | パラメータ（身長・頭身・体格）に応じたシルエットを軽量に生成・表示できる（F-11）。3D化は将来拡張として見送る |
| PDF／画像エクスポート | @react-pdf/renderer | 画面と同じコンポーネント構成でPDFを生成でき、実装・保守コストを抑えられる（F-14） |
| 差分表示 | diff（npmライブラリ） | 変更前後のテキストを比較し、変更箇所をハイライト表示する（F-13） |
| 矛盾チェック（将来） | 自作のルールチェック ＋ Gemini API（Google、無料枠・利用者が任意でオン） | 費用ゼロで運用するため、項目同士の照合は自作のルールで行い、自由記述の文章の矛盾のみGemini APIの無料枠で指摘させる。チェックを行う部品は差し替えられる構造にし、将来の有料プランや他のAIへの切り替えに備える（F-16） |
| ホスティング | 自宅サーバー（Raspberry Pi） | クラウドの月額ホスティング費用をかけず、自前の環境でアプリケーション全体を稼働させる |

## 7. 開発環境

採用方針：個人開発の規模に合わせ、環境構築の手間を増やしすぎない範囲で、開発効率が上がるツールにのみ最新技術を採用する。

| 分類 | 採用ツール | 選定理由 |
|---|---|---|
| パッケージマネージャー | pnpm | npm／yarnよりインストールが高速で、ディスク容量も節約できる |
| Node.jsバージョン管理 | Volta | プロジェクトごとにNode／pnpmのバージョンを固定し、環境差異を防ぐ |
| エディタ | VS Code | ESLint、Prisma、Tailwind CSS IntelliSense等の拡張機能が充実している |
| コード品質 | Biome（Lint＋Format） | ESLintとPrettierを1つのツールに統合でき高速。設定もシンプルに保てる |
| 型チェック | TypeScript（strict mode） | F-02〜F-14で扱うデータ構造の不整合を実装時点で検出する |
| ローカルDB | Docker（PostgreSQLコンテナ） | 課金やアカウント登録なしで、自分のPC内だけで完結させられる。`docker compose up`一発で開発用DBを起動できる |
| DB管理 | Prisma Studio | GUIでテーブルの中身を確認・編集でき、動作確認が速い |
| バージョン管理 | GitHub（main＋featureブランチ） | 個人開発のため複雑なブランチ運用はせず、機能単位でブランチを切ってmainにマージする運用とする |
| CI | GitHub Actions | push時にLint・型チェック・ビルドを自動実行し、壊れた状態のコードがmainに入らないようにする |
| デプロイ | GitHub Actions（SSH経由） | mainブランチへのマージをトリガーに、自宅サーバーへSSH接続し`git pull && docker compose up --build -d`を自動実行する |
| テスト | Vitest（最低限のユニットテスト） | F-13差分表示やF-07相関図まわりのデータ加工など、ロジックが複雑な箇所にのみ絞って導入する |

備考：Storybookや大規模なE2Eテスト基盤（Playwright等）は個人開発の規模に対して過剰と判断し、今回は採用しない。必要になった場合に追加を検討する。
なお、ローカル開発・本番公開ともにDockerベースの構成を用い、クラウドサービスの月額費用をかけない。本番公開用のサーバーは「8. 本番環境（自宅サーバー）」を参照。

## 8. 本番環境（自宅サーバー）

採用方針：クラウドのホスティング費用をかけず、Raspberry Piによる自宅サーバーで本番公開する。可用性はクラウドサービスに劣る前提を受け入れたうえで、個人開発のコストゼロ運用を優先する。

| 項目 | 内容 |
|---|---|
| 本体 | Raspberry Pi 4／5（メモリ4GB以上推奨） |
| ストレージ | USB接続SSD（起動ディスク・DB・画像データ用。SDカード単体での運用は劣化が早いため避ける） |
| OS | Raspberry Pi OS（64bit）または Ubuntu Server（ARM版） |
| コンテナ管理 | Docker Compose（開発環境と同一の構成ファイルをそのまま本番でも使用） |
| リバースプロキシ・SSL | Caddy（Let's EncryptによるSSL証明書の取得・更新を自動化し、設定もシンプルに保てる） |
| 動的IP対策 | DDNS（Cloudflare DDNSまたはDuckDNS等の無料サービス）で固定ドメインとIPを紐づける |
| ネットワーク | ルーターで80／443番ポートをPiへポートフォワーディング |
| デプロイ | GitHub Actions → SSH経由でPiにログインし、`git pull && docker compose up --build -d`を実行 |
| 稼働監視 | UptimeRobot等の無料監視サービスでダウンを検知し、通知を受け取る |
| バックアップ | PostgreSQLの定期ダンプと画像データを、外部の無料クラウドストレージへ定期的に退避する（本体故障時のデータ消失を防ぐ） |

備考：自宅の電源・回線に可用性が依存するため、停電やルーター再起動時には一時的にアクセスできなくなる。これは個人開発におけるコストと可用性のトレードオフとして受け入れる。停電対策として、小型UPS（無停電電源装置）の導入も検討する。
