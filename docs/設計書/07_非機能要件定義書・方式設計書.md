# 非機能要件定義書・方式設計書

| 項目 | 内容 |
|---|---|
| システム名 | Artリーブ |
| 文書番号 | C101-07 |
| 版 | ver1.0 |
| 関連文書 | 機能定義書「5. 非機能要件」「8. 本番環境」、08_インフラ・ネットワーク構成図 |

本書は機能定義書の非機能要件・本番環境の内容を、数値目標と実現方式まで具体化したものである。個人開発・自宅サーバー運用の規模に合わせ、守れない目標は置かない。

## 第1部 非機能要件

### 1. 可用性

| 項目 | 目標 | 備考 |
|---|---|---|
| 稼働時間 | 24時間365日（ベストエフォート） | 自宅の電源・回線に依存するため保証はしない |
| 月間稼働率 | 99%以上を目標（月7時間程度までの停止を許容） | UptimeRobotで計測 |
| 計画停止 | 深夜帯（2:00〜5:00）に実施 | OS更新・再起動 |
| 停止検知 | 5分以内 | UptimeRobotが`/api/v1/health`を5分ごとに確認しメール通知 |
| 停電時 | 自動で復帰すること | 通電時にPiが起動し、Dockerのコンテナが`restart: unless-stopped`で自動起動する |

### 2. 性能

| 項目 | 目標 | 条件 |
|---|---|---|
| 画面の初期表示 | 3秒以内 | 一般的な光回線、キャラ100体程度 |
| 画面内の操作（保存・検索） | 1秒以内に結果表示 | |
| サイドバーの開閉 | 0.3秒以内 | 資料はキャッシュを利用 |
| イラストアップロード | 10MBの画像1枚で10秒以内（変換含む） | |
| PDF書き出し | 5キャラで15秒以内 | |
| 想定データ量 | ユーザー数：少数（本人＋閲覧者）、キャラ：1ユーザー500体、イラスト：1キャラ50枚 | |
| 同時アクセス | 10人程度 | 公開ページ（将来）の閲覧を想定 |

### 3. 容量

| 対象 | 見積もり | 対応 |
|---|---|---|
| 画像 | 原本平均5MB＋変換後1MB × 1,000枚 ≒ 6GB | 256GB以上のSSDを用意 |
| DB | 数百MB程度 | 同上 |
| バックアップ（ローカル） | DBダンプ7世代＋週次4世代 | 同上 |
| 外部クラウド | DBダンプ＋画像 ≒ 10GB以内 | 無料枠の範囲で運用（10_バッチ処理設計書参照） |

ディスク使用率が80%を超えたら通知する（運用手順書参照）。

### 4. セキュリティ

| 項目 | 要件 |
|---|---|
| 通信 | すべてHTTPS。HTTPはHTTPSへ転送。HSTSを有効化 |
| パスワード | argon2idでハッシュ化。8文字以上・英数字混在 |
| ログイン試行 | 同一メールアドレス・同一IPで5回失敗すると15分ロック |
| セッション | HttpOnly・Secure・SameSite=LaxのCookie。有効期限30日 |
| 認可 | 全データアクセスでログインユーザーのIDによる絞り込みを強制（他人のデータは404） |
| CSRF | Server ActionsとAuth.jsの標準対策を利用。独自APIもSameSite Cookie＋Originヘッダー確認 |
| 入力 | Zodで全入力を検証。表示時はReactのエスケープに任せ、HTMLを直接埋め込まない |
| ファイル | 形式は先頭バイトで判定、20MB上限、保存ファイル名はUUIDにして利用者の指定名を使わない |
| 秘密情報 | `.env`はGitに含めない。サーバー上では権限600で保存 |
| 外部への送信（将来） | 利用者の設定データを外部に送るのは、本人が同意してオンにしたAIチェック（F-16）のみ。送る範囲は文章に限り、画像・アカウント情報は送らない |
| 自宅ネットワーク | 外部に開けるポートは80／443のみ。SSHはインターネットに公開せず、Tailscale経由でのみ接続 |
| 更新 | OS・Dockerイメージ・npmパッケージを月1回更新（運用手順書参照） |

### 5. データ保全

| 項目 | 目標 |
|---|---|
| RPO（どの時点まで戻せるか） | 24時間（毎日のバックアップ） |
| RTO（復旧にかかる時間） | 1日以内（SSD故障時も含む） |
| 保管場所 | 本体SSD＋外部クラウドストレージの2か所 |
| 変更履歴 | すべての設定変更を記録し、利用者自身が過去の状態に戻せる（F-13） |
| 復旧訓練 | 月1回、別環境へのリストアを試す（14_バックアップ・リストア手順書） |

### 6. 操作性・アクセシビリティ

- 主要な操作は3クリック以内で到達できる（例：図鑑→キャラ→パレット確認）。
- キーボード操作：サイドバー開閉（`]`）、イラスト切替（←→）、保存（Ctrl＋S）。
- 文字と背景のコントラスト比4.5:1以上（WCAG 2.1 AA）。ダークテーマでも確保する。
- 色だけで情報を伝えない（相関図の線はラベルを併記）。
- アニメーションを減らす設定（prefers-reduced-motion）に従う。

### 7. 互換性

| 項目 | 対応範囲 |
|---|---|
| ブラウザ | Chrome、Edge、Safari、Firefoxの最新版 |
| 画面幅 | 1280px以上（主対象）、768px以上（タブレット） |
| 書き出しファイル | PDF（A4縦）、PNG |

### 8. 保守性

- TypeScriptのstrictモード、Biomeによる自動整形・静的解析を必須とし、CIで確認する。
- 依存関係は月1回更新。メジャーバージョンアップはブランチで動作確認してから取り込む。
- 本番と開発で同じDocker構成を使い、「開発では動くが本番で動かない」を防ぐ。

## 第2部 方式設計

### 1. 認証方式

| 項目 | 方式 |
|---|---|
| ライブラリ | Auth.js（Credentialsプロバイダー） |
| セッション | JWT（Cookie保存）。DBにセッションテーブルを持たない |
| パスワード | `@node-rs/argon2`（ARM64向けのビルド済みバイナリがありPiでもビルド不要） |
| 試行制限 | メモリ内カウンタ（アプリは1台構成のため外部ストアは不要） |
| パスワード再設定 | ランダムな32バイトのトークンをメールで送り、DBにはSHA-256ハッシュのみ保存。有効期限30分 |
| メール送信 | nodemailer＋GmailのSMTP（アプリパスワード）。無料で運用できる |

### 2. 画像処理方式

```
アップロード → 先頭バイトで形式判定 → 原本保存 → Sharpで変換 → DB登録
                                          ├ display：長辺1600px WebP（品質85）
                                          └ thumb  ：長辺400px  WebP（品質80）
```

| 項目 | 方式 |
|---|---|
| 保存場所 | `/srv/artleave/uploads/{userId}/{characterId}/{illustrationId}/{original|display|thumb}.{ext}` |
| 配信 | Next.jsのRoute Handler（I06）が所有者を確認してから返す。Caddyで直接配信しない（非公開データのため） |
| キャッシュ | `Cache-Control: private, max-age=86400`。差し替え時はURLに更新日時を付けて古いキャッシュを使わせない |
| 失敗時 | DB登録に失敗したら保存済みファイルを削除。残ってしまったファイルは週次バッチで掃除（B-04） |
| メタデータ | 原本以外は撮影情報などのメタデータを削除して保存 |

### 3. 変更履歴方式（F-13）

| 項目 | 方式 |
|---|---|
| 記録単位 | 1回の保存操作＝1レコード |
| 記録内容 | 変更前・変更後のスナップショット（JSON）。差分は表示時に計算する |
| 記録のタイミング | データ更新と同じトランザクション内（ドメイン層の共通関数`withHistory()`を通す） |
| 対象外 | 相関図のノード位置、サイドバー表示キャラ、テーマ設定（見た目の状態で、設定内容ではないため） |
| 差分計算 | `diff`ライブラリ。短い項目は値の比較、長文は文字単位 |
| 削除の扱い | 削除時は関連データ（タグ・用語の紐づけ等）もbefore_jsonに含め、復元時に再現する |
| 保持期間 | 無期限（容量が問題になった場合は対象ごとに最新200件を残す方式を検討） |

### 4. 検索方式（F-04）

- タグ・種族・陣営はインデックスを使った完全一致。
- キーワードはPostgreSQLの拡張機能`pg_trgm`による部分一致（日本語の2〜3文字の検索にも対応）。
- 条件はURLのクエリに持たせ、サーバー側で検索した結果を表示する。

### 5. 相関図方式（F-07）

- 描画：React Flow。
- 自動レイアウト：位置が保存されていないノードだけ、dagreで配置する。
- 位置保存：ドラッグ終了時にまとめて送信（連続送信を避けるため500ms待ってから送る）。

### 6. マネキン描画方式（F-11）

- ポーズマスタのSVGテンプレートに、身長・頭身・体格・肌の色を差し込んでシルエットを描く。
- 頭の高さ＝身長÷頭身として頭身ガイド線を引く。
- 他キャラとの比較は、同じ縮尺で複数のSVGを重ねて表示する。

### 7. 書き出し方式（F-14）

- PDF：`@react-pdf/renderer`でサーバー側で生成。日本語フォント（Noto Sans JP）を埋め込む。
- PNG：同じレイアウトをSVGで組み、Sharpで画像に変換。複数キャラはZIPにまとめる。
- 1回20キャラまで。Piの負荷を抑えるため、同時に実行する書き出しは1件に制限し、2件目は待たせる。

### 8. ログ方式

| 種類 | 出力先 | 内容 |
|---|---|---|
| アプリログ | 標準出力（JSON） | 日時、レベル、リクエストID、ユーザーID、処理内容、エラー内容 |
| アクセスログ | Caddy（JSON） | 日時、IP、メソッド、パス、ステータス、応答時間 |
| バッチログ | `/srv/artleave/logs/batch/` | 各バッチの開始・終了・結果 |

DockerのログはJSONファイル形式で1ファイル10MB×3世代までに制限する。

### 9. 設定値の管理方式

| 環境変数 | 用途 |
|---|---|
| DATABASE_URL | DB接続文字列 |
| AUTH_SECRET | JWT署名用の秘密鍵（32バイト以上のランダム値） |
| AUTH_URL | 公開URL（例：`https://artleave.example.com`） |
| UPLOAD_DIR | 画像保存先（コンテナ内パス`/data/uploads`） |
| SMTP_HOST／SMTP_USER／SMTP_PASS | メール送信 |
| GEMINI_API_KEY | 将来のF-16用（Google AI Studioで無料発行。支払い情報を登録していないプロジェクトのキーを使い、意図せず課金されないようにする） |

開発用は`.env.local`、本番用はPi上の`/opt/artleave/.env`に置き、どちらもGitには含めない。リポジトリには値を空にした`.env.example`のみ置く。

### 11. 矛盾チェック方式（F-16、将来）

方針：月額0円を守るため、自作のルールチェックを基本とし、Gemini APIの無料枠によるAIチェックは利用者が選んだ場合だけ追加する。

#### 11.1 構成

チェックを行う部品を共通の形（インターフェース）にそろえ、差し替えや追加ができるようにする。

```ts
// src/server/services/consistency/types.ts
export interface ConsistencyChecker {
  name: "rule" | "ai";
  check(context: CheckContext): Promise<Finding[]>;
}
```

| 部品 | 実装 | 実行のしかた |
|---|---|---|
| RuleChecker | 自作。ルールR-01〜R-06（機能定義書F-16）を1ルール1関数で実装 | 依頼を受けたその場で実行（数十ミリ秒） |
| GeminiChecker | `@google/genai`でGemini API（無料枠対象のFlash系モデル）を呼ぶ | 非同期。アプリ内のキューで1件ずつ処理 |

将来、Geminiの有料プランや別のAIに変える場合は、GeminiCheckerの代わりの部品を作って差し替えるだけで済む。

#### 11.2 ルールチェックの実装方針

| ルール | 方法 |
|---|---|
| R-01 関係の向き | 「兄⇔弟」「姉⇔妹」「親⇔子」「師匠⇔弟子」などの対になるラベルの辞書を持ち、A→BとB→Aのラベルが対になっていなければ指摘 |
| R-02 色の食い違い | プロフィール文から「（色名）＋瞳／目／髪」を正規表現で抜き出し、色名の色相範囲と、パレットの同じ用途の色（HEXを色相に変換）を比べる |
| R-03 身長の食い違い | プロフィール文から「身長◯cm」を抜き出し、マネキンの身長と3cm以上違えば指摘 |
| R-04 時系列の逆転 | 作中時期ラベルの最初の数字（年）を取り出し、並び順（story_order）と大小が逆になっているエピソードを指摘 |
| R-05 重複・表記ゆれ | 名前・種族・陣営を正規化（全角半角、ひらがなカタカナ、空白をそろえる）して同じになるものを指摘 |
| R-06 登録漏れ | エピソード本文に含まれるキャラ名のうち、関連キャラに登録されていないものを指摘 |

ルールは文章の意味までは理解できないため、指摘はすべて「確認をおすすめします」という表現にする。

#### 11.3 AIチェックの方式

| 項目 | 方式 |
|---|---|
| 送る内容 | 対象と関連する設定（関連キャラ・用語・エピソード）の文章のみ。画像・アカウント情報は送らない。1回あたりの文字数に上限を設け、超える場合は関連度の高いもの（直接紐づいているもの）から優先して送る |
| 応答の形式 | Gemini APIの構造化出力（JSONスキーマ指定）で、指摘の配列（該当箇所、根拠となる既存設定の引用、指摘文）を受け取る |
| 結果の確認 | AIが返した引用が、実際の設定文に含まれているかをコードで確認し、含まれていない指摘（AIの作り話）は捨てる |
| タイムアウト | 60秒。超えたら`partial`（ルールの結果のみ表示） |
| 回数制限 | 1ユーザー1分に1回・1日50回まで。Gemini側の回数制限（429）を受けた場合も`partial`にして、時間をおいた再実行を案内する |
| 同意 | 無料枠では送った内容がGoogleのサービス改善に使われるため、AIチェックは初期状態オフ。設定画面で説明を読み、同意した利用者だけがオンにできる |
| 鍵の管理 | APIキーは環境変数`GEMINI_API_KEY`に置き、画面側（ブラウザ）には一切出さない。支払い情報を登録していないプロジェクトのキーを使い、課金が発生しないようにする |
