## 第1部 テスト計画書

### 1. 目的

機能定義書の各機能が仕様どおりに動くこと、特に本サービスの中心である「設定を失わない・崩さない」（変更履歴、所有者チェック、バックアップ）が確実に機能することを確認する。個人開発の規模に合わせ、自動テストはロジックの複雑な箇所に絞り、それ以外は手動テストで確認する。

### 2. テストレベルと範囲

| レベル | 方法 | 対象 | 実施タイミング |
|---|---|---|---|
| 単体テスト | Vitest（自動） | ドメイン層のロジック：変更履歴の差分計算・復元、用語ツリーの循環チェック、検索条件の組み立て、入力検証スキーマ、マネキンのシルエット計算 | push・PRごとにCIで実行 |
| 結合テスト | Vitest＋テスト用DB（Docker）（自動） | サービス＋DB：所有者チェック（他人のデータが見えない）、履歴が同一トランザクションで残ること、カスケード削除 | push・PRごとにCIで実行 |
| システムテスト | 手動（テスト仕様書に沿って実施） | 画面操作を含む全機能 | 各フェーズの完了時 |
| 非機能テスト | 手動＋計測 | 性能・セキュリティ・停電復帰・バックアップからの復元 | Phase 1完了時と本番公開前 |
| 受け入れテスト | 手動 | 実際にオリキャラを10体以上登録して作業に使い、使い勝手を確認 | 本番公開前 |

対象外：E2E自動テスト（Playwright等）、負荷試験ツールによる大規模な負荷テスト（規模に対して過剰なため）。

### 3. テスト環境

| 環境 | 構成 | 用途 |
|---|---|---|
| ローカル | 開発PC＋Docker（PostgreSQL） | 単体・結合・システムテスト |
| CI | GitHub Actions（PostgreSQLのサービスコンテナ） | 単体・結合テストの自動実行 |
| 本番相当 | Raspberry Pi（本番と同じ構成） | 非機能テスト、受け入れテスト |

テストデータはシードスクリプト（`prisma/seed.test.ts`）で、キャラ30体・イラスト100枚・用語50件・エピソード30件・関係40件を作成する。性能テスト用にはキャラ500体の大量データ版も用意する。

### 4. 開始・完了の基準

| 区分 | 基準 |
|---|---|
| 開始 | 対象機能の実装が完了し、CI（Lint・型チェック・ビルド）が通っている |
| 完了 | ・自動テストがすべて成功<br>・ドメイン層（`src/server/services`）の行カバレッジ80%以上<br>・手動テストの重要度「高」が全件合格、「中」以下は未解決が残る場合も理由と対応予定を記録<br>・不具合一覧に未対応の「致命的」がない |

### 5. 不具合の管理

GitHubのIssueで管理する。ラベルで重要度を付ける。

| 重要度 | 定義 | 対応 |
|---|---|---|
| 致命的 | データの消失・他人のデータが見える・サービスが使えない | 即時修正。修正までリリースしない |
| 高 | 主要機能が使えない | 当該フェーズ中に修正 |
| 中 | 回避策がある不具合 | 次のフェーズまでに修正 |
| 低 | 見た目の崩れなど | 余裕があれば修正 |

### 6. スケジュール

| フェーズ | テスト内容 |
|---|---|
| Phase 1 完了時 | F-01〜F-05、F-09、F-13のシステムテスト、セキュリティテスト |
| Phase 2 完了時 | F-06〜F-08、F-10、F-11のシステムテスト、Phase 1機能の回帰確認 |
| Phase 3 完了時 | F-12、F-14のシステムテスト、全機能の回帰確認 |
| 本番公開前 | 非機能テスト（性能・停電復帰・リストア）、受け入れテスト |
